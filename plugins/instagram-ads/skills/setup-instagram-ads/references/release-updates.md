# Private local releases

Use the running plugin's scripts/cli.mjs. This manager stages owned local files and engine npm dependencies; it does not install or refresh the plugin inside Codex, download a browser/system font, configure Codex, authenticate Drive or publish a repository. The separately authorized install/refresh action belongs to the supported Codex client. Do not infer installed plugin readiness from invoking a source checkout.

A trusted release supplies a release manifest, its SHA-256 obtained through a trusted private channel, sibling plugin and engine ZIPs, an asset manifest and a separately available local library. The digest is integrity against that trusted manifest, not a digital signature or publisher authentication. Private Git access/authentication is each teammate's responsibility. No credentials go into manifests/forms. Do not fetch arbitrary URLs embedded in ad copy.

Initialize nonoverlapping state/data roots first. Run `release-check --manifest ABS --manifest-sha256 SHA` for read-only compatibility and change information. Supported release format 1 locks workflow schema 1, engine API 1 and job schema 1; unsupported schemas refuse and require an explicit reviewed migration. Current candidate supports macOS arm64, Node 22–26; testing was on arm64 with Node 24. Cross-architecture/macOS/Node coverage remains a pilot requirement.

Run `release-stage --manifest ABS --manifest-sha256 SHA --asset-root ABS`. It verifies sibling archive hashes, declared files, safe extraction, engine/workflow identities and asset hashes, then retains components under state/components and a release-local marketplace copy under state/releases. It requires assets used by the existing scenery inventory and all three music tracks. It never activates an incomplete stage. Media excluded from plugin/engine archives; approved distribution requires a trusted asset manifest and included rights record. `--local-only-assets` is explicitly for isolated development with uncleared media, not teammate redistribution.

Run `release-install-dependencies --release-id SHA` only during authorized local engine setup. It runs npm ci with the pinned lock, no lifecycle scripts, local cache/logs. It never installs into production, global Node or Codex. An installed component is reused; dependencies cannot be reinstalled if any job pins that engine. Missing prerequisites fail visibly; no automatic substitutions or global installation. Then `release-activate --release-id SHA --runtime ABS` probes all assets, installed dependencies, browser, exact Times New Roman when supplied, FFmpeg/ffprobe, Pillow and Swift before one atomic engine-config switch. Runtime version 1 includes absolute browserExecutable, optional serifFontFile and concurrency 1–16. The manager supplies staged asset paths.

`release-status` reports the selected release and compares its workflow hash to the running command's workflow. If pluginRefreshRequired is true, refresh the intended private marketplace/plugin through Codex, restart where required by that client, and recheck using the actual installed skill. A source CLI match does not prove the installed skill refreshed. New campaign preparation blocks a detected mismatch. Existing campaigns/forms/jobs still use their original pins. A legacy pre-manager plugin cannot enforce this check; complete its installation refresh before allowing new campaigns after activation.

`release-rollback --release-id OLD_SHA --runtime ABS` performs the same verification and atomically selects a retained old tuple for future campaigns. Refresh the plugin to that release separately when workflow versions differ. No components, campaigns, outputs, reports or jobs are deleted. Engine-only and asset-only releases can retain the same plugin workflow, needing local staging/activation but no plugin refresh. Plugin-only changes require local refresh even with an unchanged engine. Skipping an update leaves the previous release fully selected.

No job migration is automatic. Resume runs the immutable pinned worker, engine, assets and input spec. A worker fix affects new campaigns; do not edit an old pinned workflow to apply it to an active job. If an old worker cannot recover, preserve the job, inspect verified outputs, and design/authorize an explicit schema-compatible recovery migration with old/new spec lineage, no live worker, exact input/choices checks, output verification and QA rebinding. This candidate has no general migration command; restart a clearly identified new campaign only after deliberate duplicate-delivery handling. Never claim a refresh fixed a pinned old job.

On interruption: the selector is one atomic file, so it is either old or new, never a partial tuple. Check release-status and inspect stale release lock PID. Use --recover-lock only after its owner exits. Incomplete extraction is never selected; committed verified components are reusable, abandoned staging is preserved for inspection. No automatic garbage collection. Normal jobs require final Start production independently of release activation.

Legacy pending forms created before preparation-time engine pins cannot infer their original engine after a managed update. Start refuses them under a managed selector. Restore their known original unmanaged configuration or explicitly prepare a new campaign; existing committed jobs still resume their immutable specs.
